0-1背包问题6步搞懂

2026-09-01

背包问题（Knapsack Problem）是组合优化中的 NP 完全问题，最基础的两个变体是 0-1 背包 和 完全背包。它之所以值得反复琢磨，是因为「选 or 不选」的决策模型几乎渗透在每一个日常决策里；而没真正搞懂之前，很容易产生「我已经会了」的错觉。

本文以分割等和子集（LeetCode 416）为例，走完一条完整的演进路线：

递归暴力枚举 $O(2^n)$ → 记忆化递归 → DP 状态转移

前六步是主线，最后一步位运算是彩蛋，仅供开阔思路。

例题

给你一个只包含正整数的非空数组 nums。判断是否可以将这个数组分割成两个子集，使得两个子集的元素和相等。

例如 nums = [1, 5, 11, 5]，总和为 22，可以分成 [1, 5, 5] 与 [11]，两者和都是 11，返回 True。

这个问题等价于：能否从 nums 里选出若干个数，让它们的和恰好等于 total / 2（total 为总和）。这就是一个标准的 0-1 背包判定问题——容量 target = total / 2，每个数的体积等于自身值，问能否恰好装满。若 total 为奇数，必然无法均分，直接返回 False。

以下所有方法均使用 List 类型注解，LeetCode 环境已默认导入 from typing import List，本地运行请自行补充。

1、暴力递归：一切的出发点

不从 DP 直接开始，是因为状态转移方程的「手感」是从递归里长出来的。定义递归函数：

$$dfs(i, s)=\text{从第 }i\text{ 个元素开始考虑，当前已累计和为 }s\text{，能否凑出 }target$$

对每个元素，递归状态树上有两条边：选（pick）或 不选（no_pick）。只要有一条路能通，当前状态就为 True。

两个边界条件值得单独拎出来说：

  • s == target 是成功条件，放在最前面，一旦命中立刻短路；
  • i >= n or s > target 是失败条件。i >= n 表示所有元素都决策完了还没凑够；s > target 是剪枝——因为 nums 全为正数，一旦超了就永远回不来了。

复杂度：每个元素有两条边，最坏情况状态树有 $2^n$ 个节点，时间复杂度 $O(2^n)$；递归栈深度最多 $n$ 层，空间复杂度 $O(n)$。

2、记忆化递归：剪掉重复的枝

暴力递归慢，慢在大量重复子问题：dfs(i, s) 的结果只和 (i, s) 有关，和怎么走到这一步无关。同一个 (i, s) 可能被不同的路径重复计算。用一个 mem[i][s] 把算过的结果缓存下来，第二次遇到直接返回。

这里用 None 表示「尚未计算」，而不是用 False——因为 False 是一个合法的计算结果，混用会误判成「没算过」而重复计算。

复杂度：状态数不超过 $(n+1) \times (target+1)$，每个状态只算一次、代价 $O(1)$，时间复杂度 $O(n \cdot target)$；mem 数组占 $O(n \cdot target)$，递归栈 $O(n)$，空间复杂度 $O(n \cdot target)$。

3、后缀视角的 DP：自底向上

观察记忆化递归的调用方向：求 dfs(i, s) 需要先求 dfs(i+1, ...)。也就是说，答案依赖下标更大的子问题。把这层依赖关系显式化，就得到 DP 的转移方程，i 需要从大到小循环。

定义 dp[i][s]：处理 nums[i..n-1] 这些数，能否凑出 s（后缀视角）。转移：

$$dp[i][s] = dp[i+1][s]\ \text{or}\ dp[i+1][s+nums[i]]$$

其中 dp[i+1][s] 是不选 nums[i]，dp[i+1][s+nums[i]] 是选 nums[i]（前提 s + nums[i] <= target）。

三个细节：

  1. 哨兵行 dp[n][s] = (s == target)。dp[n] 表示「已经处理完所有元素」，此刻只有累计和恰好等于 target 才算成功，这正是递归里 if s == target: return True 的 DP 形态。
  2. 转移里的 <= target 不能写成 < target。若漏掉等号，s + nums[i] == target 的路径会被 else 分支吞掉，导致 dp[n][target] 这个唯一的 True 永远传不上去，最后恒为 False。
  3. False 与 None 的区别。这里默认值用 False 而非 None，因为 DP 是自底向上把所有状态都算一遍，不存在「没算过」的状态，也就不需要 None 做标记。

复杂度与记忆化相同：时间 $O(n \cdot target)$，空间 $O(n \cdot target)$。

4、前缀视角的 DP：从前往后

后缀视角不太直观，更多人习惯「前 $i$ 个元素」的前缀视角。把定义改成：

$$dp[i][s]=\text{前 }i\text{ 个元素 }nums[0..i-1]\text{ 能否凑出 }s$$

转移方程对称地变为：

$$dp[i][s] = dp[i-1][s-nums[i-1]]\ \text{or}\ dp[i-1][s]$$

下标 i-1 是当前正在决策的元素，dp[i-1][s-nums[i-1]] 是选它，dp[i-1][s] 是不选它。

初始化 dp[0][0] = True（0 个元素凑出 0），这也是递归里 s == target 在对偶视角下的边界。dp[-1][-1] 即 dp[n][target]。

5、两行滚动数组：先砍掉一个维度

观察前缀 DP 的转移：dp[i] 只依赖 dp[i-1]，更早的行永远不再被访问。既然只用到上一行，就用 prev 和 curr 两个一维数组轮流替换，把空间从 $O(n \cdot target)$ 降到 $O(target)$。

6、一维 DP 与反向遍历

还能再进一步：连 curr 也不要，就地复用 prev 一个数组。关键矛盾在于——dp[s] 的更新要用到上一轮的旧值，如果从小的 s 正向更新，小的 s 先被改写，后面大的 s 读到的就是本轮已污染的值，等于把同一个物品用了多次，退化成完全背包。

解法是反向遍历：让 s 从大到小更新，保证计算 dp[s] 时，dp[s - nums[i-1]] 还停留在上一轮、尚未被本轮改写。

两个容易写错的点：

  1. dp[0] = True 不能漏。不选任何数凑出 0，是所有状态的起点。
  2. 等式右边是 dp[s]，不是某个别的下标。这里的 dp[s] 代表「不选 x」的旧状态，dp[s - x] 代表「选 x」的旧状态，二者取或。range(target, x - 1, -1) 同时保证了 s - x >= 0，省去了显式的越界判断。

顺带一提，0-1 背包与完全背包的一维代码长得几乎一样，唯一区别就是遍历方向：0-1 背包反向（每个物品只用一次），完全背包正向（物品可无限用）。理解了反向遍历的动机，就能记住这个方向。

7、彩蛋：位运算 bitset

判定型背包本质上是在维护一个「哪些和可以凑出来」的集合。用一个二进制数 f 表示这个集合：f 的第 s 位为 1，表示能凑出 s。初始 f = 1（只有第 0 位为 1，能凑出 0）。对每个物品 x：

$$f = f\ |\ (f \ll x)$$

f << x 把当前所有可凑出的和整体加 x，代表「选这个物品」；再和 f 取或，代表「不选」的分支也保留。最后看 f 的第 target 位是否为 1。

注意 f >> s & 1 的优先级：移位 >> 高于按位与 &，所以它等价于 (f >> s) & 1，先右移再取最低位。Python 大整数让 f 可以任意长，但单次移位、取或的代价随位数增长，严格来说并不是 $O(1)$；忽略这个常数，它是最紧凑、最「有味道」的写法。

方法 时间复杂度 空间复杂度 核心思想
1 暴力递归 $O(2^n)$ $O(n)$ 二叉状态树
2 记忆化 $O(n \cdot target)$ $O(n \cdot target)$ 缓存子问题
3 后缀 DP $O(n \cdot target)$ $O(n \cdot target)$ 自底向上
4 前缀 DP $O(n \cdot target)$ $O(n \cdot target)$ 自顶向下
5 两行滚动 $O(n \cdot target)$ $O(target)$ 只存两行
6 一维 DP $O(n \cdot target)$ $O(target)$ 就地复用 + 反向
7 位运算 $O(n \cdot target/w)$ $O(target/w)$ bitset（$w$ 为字长）

课后思考：双约束背包

有 $n$ 个任务，系统最多提供 $A$ 单位内存和 $B$ 单位算力。第 $i$ 个任务执行消耗 $x_i$ 单位内存、$y_i$ 单位算力，获得收益 $w_i$。选择若干任务执行以最大化总收益；在收益最大的所有方案中，优先内存总消耗更小的，若仍相同则优先算力总消耗更小的。

这是把背包的容量从一维扩展到二维：状态既要限内存，又要限算力。记 dp[a][b] 为「内存不超过 $a$、算力不超过 $b$ 时能取得的最大收益」，转移时对每个任务、两个维度都要反向遍历，避免重复使用：

$$dp[a][b] = \max\big(dp[a][b],\ dp[a-x_i][b-y_i] + w_i\big)$$

空间优化：a、b 两个维度都反向遍历，直接在一张二维 dp 表上原地更新即可，无需三维。真正难点在第二个要求——字典序比较。收益相同要比较两个消耗，一个常用技巧是：额外维护一张同尺寸的 cost[a][b] 记录「取得 dp[a][b] 这份收益时的总内存消耗」，当 dp[a][b] 被某个方案追平时，比较该方案的内存消耗是否更小，是则更新 cost[a][b]（算力同理作为第二关键字）。这样把「多关键字比较」拆成 DP 值之外的辅助表，比在 DP 值里编码字典序更清晰，也更好调试。
